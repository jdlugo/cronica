# Daily Puzzle Analytics KPI Spec

## Goal
Define measurable engagement criteria for Daily Puzzle and map each KPI to concrete telemetry events now emitted by the app.

## Event Taxonomy
All event names below are emitted through `DailyPuzzleLiveAnalyticsTracker`.

1. `daily_puzzle_open_requested`
- Trigger: user intent to open puzzle from explicit CTA.
- Metadata:
  - `source` (`notification_settings`, `push_notification`, etc.)

2. `daily_puzzle_opened`
- Trigger: puzzle sheet actually opened.
- Metadata:
  - `puzzle_id` (`YYYY-MM-DD`)
  - `source` (`home_card`, `notification_settings`, `push_notification`, etc.)

3. `daily_puzzle_guess_submitted`
- Trigger: non-empty guess submitted.
- Metadata:
  - `puzzle_id`
  - `attempts` (attempt count after submission)

4. `daily_puzzle_hint_unlocked`
- Trigger: hint threshold crossed.
- Metadata:
  - `puzzle_id`
  - `hint_level` (`1` or `2`)

5. `daily_puzzle_solved`
- Trigger: correct guess submitted.
- Metadata:
  - `puzzle_id`
  - `attempts`

6. `daily_puzzle_share_tapped`
- Trigger: share button tapped from solved state.
- Metadata:
  - `puzzle_id`
  - `attempts`

7. `daily_puzzle_prompt_shown`
- Trigger: the inline reminder action enters the view hierarchy after a daily solve, or in Notification Settings. Deduplicated per view instance.
- Metadata:
  - `puzzle_id`

8. `daily_puzzle_prompt_response`
- Legacy event: response to the retired deferred alert. New builds use notification choice and outcome events below.
- Metadata:
  - `puzzle_id`
  - `granted` (`true`/`false`)

9. `daily_puzzle_reminders_toggle_changed`
- Trigger: reminders toggle changed in Notification Settings.
- Metadata:
  - `enabled` (`true`/`false`)
  - `source` (`notification_settings`)

10. `daily_puzzle_failed`
- Trigger: the sixth incorrect guess reaches the terminal failed state.
- Metadata:
  - `puzzle_id`
  - `attempts`
  - `puzzle_index`
  - `terminal_result` (`failed`)

11. `daily_puzzle_ad_opportunity`
- Trigger: an eligible Daily Puzzle native-ad slot enters the rendered view hierarchy.
- Metadata:
  - `puzzle_id`
  - `placement` (`native_puzzle`)
  - `puzzle_index`
- This is an opportunity signal, not an AdMob impression. Financial impression truth remains in AdMob and Google ad callbacks.

All Daily Puzzle view-model events include `puzzle_index` and `terminal_result` as common context. Ad lifecycle events generated by puzzle continuation carry `trigger=puzzle_completed`, `flow=daily_puzzle_continuation`, puzzle index, result, attempts, and hint count through presentation, impression, click, and dismissal callbacks.

## KPI Definitions

1. Puzzle Open Rate (daily)
- Formula:
  - `unique_users(daily_puzzle_opened) / DAU`
- Target:
  - `> 25%`

2. Completion Rate (daily)
- Formula:
  - `unique_users(daily_puzzle_solved) / unique_users(daily_puzzle_opened)`
- Target:
  - `> 65%`

3. Median Attempts to Solve
- Formula:
  - median of `attempts` from `daily_puzzle_solved`
- Target:
  - `2-4`

4. Share Rate (among solvers)
- Formula:
  - `unique_users(daily_puzzle_share_tapped) / unique_users(daily_puzzle_solved)`
- Target:
  - `> 10%` (initial)

5. Prompt Conversion Rate
- Formula:
  - `unique_users(daily_puzzle_notification_outcome where outcome=enabled) / unique_users(daily_puzzle_prompt_shown)`
- Target:
  - `> 35%` (initial)

6. Reminder Retention Guardrail
- Formula:
  - daily `% disabled` from `daily_puzzle_reminders_toggle_changed(enabled=false)`
- Target:
  - `< 2%` per day after initial onboarding week

7. Puzzle Depth
- Formula:
  - terminal rounds (`daily_puzzle_solved` + `daily_puzzle_failed`) / unique puzzle runtime sessions
- Target:
  - increase release over release without degrading solve rate or retention

8. Continuation Load Rate
- Formula:
  - `daily_puzzle_next_loaded / daily_puzzle_next_tapped`
- Target:
  - `> 95%`

9. Interstitial Impressions per Puzzle Session
- Formula:
  - puzzle-attributed `ad_interstitial_impression / unique puzzle runtime sessions`
- Guardrail:
  - evaluate with D1/D7 retention and puzzle depth; never optimize this metric alone

- strict funnel: `daily_puzzle_opened` -> `daily_puzzle_session_started` -> `daily_puzzle_guess_submitted` -> terminal outcome
- entry-source volume: report `daily_puzzle_open_requested` separately because it covers explicit CTAs rather than every puzzle open

## Three-round Daily Run

The Daily Run is one session-local sequence of three terminal puzzles. Solved and failed puzzles both count as completed rounds.

### Events

- `daily_puzzle_run_started`: emitted once when a run's first round reaches a terminal result, so the run funnel reflects engaged rounds rather than modal opens.
- `daily_puzzle_run_completed`: emitted once after the third distinct puzzle reaches a terminal state.
- `daily_puzzle_run_shared`: emitted when the completed-run share control is tapped.
- `daily_puzzle_run_continue_tapped`: emitted when the user chooses Keep Playing from the summary.

Every run event includes `puzzle_id`, `run_sequence`, and `target_rounds`. Completion, share, and continuation events also include `completed_rounds`, `solved_rounds`, `failed_rounds`, `total_attempts`, `total_hints`, and `current_streak`. Existing puzzle context such as `puzzle_index`, `puzzle_source`, `is_archive`, and `terminal_result` remains attached by the native tracker.

### Decision metrics

- Run completion rate: `daily_puzzle_run_completed / daily_puzzle_run_started`.
- Run share rate: `daily_puzzle_run_shared / daily_puzzle_run_completed`.
- Run continuation rate: `daily_puzzle_run_continue_tapped / daily_puzzle_run_completed`.
- Run solve quality: distribution of `solved_rounds`, `total_attempts`, and `total_hints` on completed runs.

Segment each metric by app version/build, run sequence, acquisition source when available, and paid status. Compare the first full seven-day post-release window with the prior release's puzzle-depth funnel. Guardrails are next-puzzle load failures, puzzle abandonment, interstitial presentation failures, and day-1/day-7 retention.

## Five-day Weekly Movie Goal

A calendar day is credited after one complete three-round Daily Run. Additional runs remain playable and monetizable but do not add another goal day. Progress resets at the start of a new ISO week and is capped at five unique days.

### Event

`daily_puzzle_weekly_goal_updated` is emitted when a Daily Run completes. It includes `week_id`, `outcome`, `completed_days`, `target_days`, `remaining_days`, `completed_today`, and `goal_complete`, plus the existing native puzzle/build context. Valid outcomes are `progressed`, `completed`, `already_completed_today`, and `already_complete`.

### Decision metrics

- Weekly-goal exposure: unique users with `daily_puzzle_weekly_goal_updated`.
- Next-day return after exposure: exposed users who produce `app_launched` or `daily_puzzle_opened` on the following local calendar day.
- Goal progression: distribution of `completed_days` by week and app build.
- Goal completion rate: users reaching outcome `completed` divided by exposed users in the same `week_id`.
- Habit-to-revenue lift: revenue, impressions, and qualified ad opportunities per exposed puzzle starter versus the prior build.

Retain the feature when next-day puzzle return and revenue per puzzle starter improve without increased load failures, notification opt-outs, or a material decline in run completion.

## Contextual Rewarded Hint Funnel

The rewarded-hint offer is hidden at attempt zero and becomes eligible only after a wrong guess. It remains user initiated, names the next hint, and records a reward only from the existing ad-completion callback.

### Events

- `daily_puzzle_hint_offer_shown`: one impression per puzzle and hint level.
- `daily_puzzle_hint_offer_tapped`: explicit user intent to watch the ad.
- `daily_puzzle_hint_reward_granted`: the ad callback granted the promised hint.

Each event includes `puzzle_id`, `hint_level`, and `attempts`, plus native puzzle/build context.

### Decision metrics

- Hint offer tap rate: `daily_puzzle_hint_offer_tapped / daily_puzzle_hint_offer_shown`.
- Reward delivery rate: `daily_puzzle_hint_reward_granted / daily_puzzle_hint_offer_tapped`.
- Reward-assisted solve rate: rewarded puzzle IDs followed by `daily_puzzle_solved` divided by rewarded puzzle IDs.
- Rewarded revenue per offer and per puzzle starter, joined to AdMob rewarded impressions by build and time window.

Segment by hint level, attempt number, puzzle source, media type, and app build. Guardrails are puzzle abandonment after an offer, max-attempt failures, ad-unavailable outcomes, time-to-solve, and overall run completion.

## Visible puzzle activation and abandonment

For builds containing the September 29 recovery changes, use `daily_puzzle_screen_visible` as the start of the daily-game presentation funnel. Legacy `daily_puzzle_opened` and `daily_puzzle_session_started` still describe the open path before presentation and are not proof that the screen appeared.

- `daily_puzzle_screen_visible`: once when the daily game appears, or when a new puzzle replaces it. Includes source and a `presentation_id` shared by that view model's guess, solve, and hint events.
- `daily_puzzle_first_input`: once after nonblank editing (or submission) on an unfinished puzzle. No typed text is included.
- `daily_puzzle_abandoned`: once when the daily puzzle sheet is dismissed unfinished after being visible; includes `had_input`, attempts and elapsed `visible_seconds`. Temporary view disappearance for overlays does not count as abandonment. Force quit and app backgrounding are not inferred as dismissal; elapsed time can include background time.

Use an ordered funnel grouped by user and `presentation_id`: visible → first input → guess → solved/failed. Segment visibility by source. Reopened view models get a fresh presentation identity after dismissal. The standalone archive game retains its legacy telemetry and must not be mixed into the daily-game visibility denominator.

Continuation failure reasons now report sanitized URL error codes (for example `url_error_-1009`) or `loading_failed`; no error-description URLs or typed content are added to these events. Failure UI preserves progress and offers Retry, Stay Here, or the bundled Offline Puzzles archive.

## Inline reminder opt-in

The solved daily puzzle offers a nonblocking reminder action. Practice puzzles do not. Users with denied permission get a Settings link; undetermined and provisional users request full alert permission. Successful authorization explicitly enables both global notifications and puzzle reminders. Confirmation means permission and preferences are enabled, not proof of delivery. Delivery remains at 18:00 device-local time, skipped after completion.

- `daily_puzzle_notification_choice`: `action=enable` or `open_settings`.
- `daily_puzzle_notification_outcome`: `outcome=enabled`, `denied`, `error`, or `settings_unavailable`.
- Puzzle-origin events include puzzle/presentation context. Settings-origin events include `source=notification_settings`.

Separate choices from outcomes: opening Settings is not an opt-in, and declining the OS prompt is not acceptance. Compare only builds containing the new flow; old prompt telemetry was emitted before presentation. Saved insight definitions are updated locally and require an explicit import to change PostHog.

## Movie image quiz

The new client presents four title choices against a textless TMDb backdrop. Current daily records remain compatible with older clients. Three terminal rounds still complete a Daily Run. First-try correctness, assisted points, and participation are distinct:

- `movie_quiz_image`: `outcome=shown` or `unavailable`, deduplicated per view model and outcome. An unavailable image offers text clues.
- `movie_quiz_answer_selected`: `correct` and `assisted`, with `answer_mode=image_choice`, presentation ID, attempts, and `quiz_points`. No guessed titles are sent.
- `movie_quiz_hint_revealed`: `reason=requested` or `image_unavailable`. Automatic fallback is not user intent.
- `movie_quiz_skipped`: the player explicitly revealed the answer, earning zero points; the round still counts toward completion.
- `movie_quiz_load_failed`: answer preparation could not produce a valid round.
- `movie_quiz_run_scored`: total `points` out of nine, `first_try_rounds`, and the daily `participation_streak`.

A correct first answer earns three points; each eliminated wrong answer costs one, and explicitly requesting a clue costs one. A wrong answer automatically supplies a clue without an additional charge. Restored legacy completions are labeled and do not fabricate a quiz score. Finishing three rounds earns a participation day regardless of score, once per local calendar day. The existing solve streak remains separate.

Compare image shown → first answer → correct/revealed → three-round completion, segmented by release and source. Monitor image-unavailable rate separately from low engagement. This mode provides free clues rather than the old rewarded-hint placement, so the old rewarded-hint funnel is not a like-for-like comparison. Evaluate revenue per quiz starter together with completion and return rate after release.

### Tile reveal follow-up

New rounds begin with the center of a nine-tile image visible. `movie_quiz_tile_revealed` records `tile_index`, `revealed_tile_count`, and `available_points`; duplicate or invalid taps do not emit an event. `movie_quiz_answer_selected` additionally records `revealed_tile_count`, `tile_reveal_enabled`, and `image_fallback`. Compare completion and return rates alongside how many tiles players uncover; more taps alone are not evidence of greater enjoyment.

Correct tile answers earn 3 points with 1–3 visible tiles, 2 with 4–6, and 1 with 7–9 before wrong-answer/requested-clue deductions, with a floor of 1 for a correct answer. Missing-image fallback clues are free. Old saved rounds retain their previous scoring. Segment by tile mode before comparing scores across versions.

New second rounds also support zoom reveals. `movie_quiz_zoomed_out` records `zoom_step` (1 or 2) and `available_points`; answer events carry `zoom_step` (`none` for non-zoom rounds). Separate these rounds from tile mode when comparing assistance usage and completion. Each requested zoom-out changes the maximum from 3 to 2 to 1, with existing wrong-answer and clue deductions and a one-point floor.

Four-round runs now report `target_rounds=4` and a maximum of 12 points. Segment run-completion comparisons by `target_rounds` or app version: the fourth-round requirement changes the funnel relative to earlier three-round runs. New rounds alternate tiles/zoom; persisted puzzle states retain their existing reveal mode.
